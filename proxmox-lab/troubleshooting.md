# Quick troubleshooting

*Part of the [Proxmox lab guide](README.md).*

- **An NVMe drive isn't visible at install** → VMD/RST in BIOS (Stage 0.1).
- **A node stopped seeing its NVMe drives, or won't boot, right after a BIOS update** → the flash reset the settings to defaults and VMD/RST came back on. Redo Stage 0.1 in full — VT-x/VT-d and "restore on AC" are gone too, and the last one fails silently until the next power cut (16.3, "After every flash").
- **A node is unreachable after a BIOS update, both corosync rings down** → the NICs were renamed, so `/etc/network/interfaces` now configures nothing. Physical console, then the same fix as a disk transplant: new names in, `ifreload -a` (19.3 step 5 / 16.3).
- **Replication fails** → does a pool with the same name exist on the target? Does it have space? (`zpool list`)
- **Replication says `storage 'apps' is not available on node 'pve2'`, but the pool is right there in Disks → ZFS** → the pool exists, the *storage definition* is pinned to pve1 — Stage 6's *Add Storage* checkbox writes `nodes <that node>`, and the join discarded pve2's own copy of `storage.cfg`. `pvesm set apps --delete nodes` (same for `db`), then re-run the job (Stage 6).
- **[`cluster-health`](scripts/README.md) mails `[FAIL] replication: 1020-0(SYNCING, fails=0) — your RPO is drifting right now` every morning, and `pvesr status` is clean by the time you look** → nothing is wrong with replication; the check on that node is out of date. `pvesr` builds that column as `$job->{pid} ? "SYNCING" : $job->{error} // 'OK'`, so it holds exactly one of three things — `SYNCING` (a run holds a pid *right now*), `OK`, or the literal error text — and the old check flagged anything that wasn't the literal `OK`. Jobs 1020-0, 1021-0 and 1023-0 are `schedule *:0` and fire at `HH:00:00`–`:09`; the cron entry ran at `07:00:01`, three to six seconds inside them, so it caught a healthy in-flight sync nearly every day. Fixed at both ends on 2026-09-10: the check accepts `SYNCING` while `FailCount` is 0, and the entry moved to **07:07**, which clears those three. The move is tidiness, not the fix — 1022-0 is `*/1` and fires 1440 times a day, so no cron minute dodges it; the `SYNCING` rule is the part that makes the check right. Still seeing it ⇒ this node is running the pre-fix copies — `ls -l /usr/local/sbin/cluster-health`, and `grep cluster-health /etc/cron.d/pve-helper-scripts` (a `0 7` line is the tell). Re-run [`install-scripts.sh`](scripts/README.md) on both nodes ([2.4](setup/02-post-install.md#24-install-the-helper-scripts-both-nodes)); it is also the run that puts `PATH` into the cron file, the fault behind the false NVMe `[FAIL]`s further down this list. Do that rather than living with it: a red line that means nothing every single morning is how the one that means something gets skimmed past.
- **Migration is slow** → on this build that is the design, not a fault: `datacenter.cfg` pins migration and replication to the 1G LAN because the 10G cable is normally unplugged ([5.2](setup/05-network.md#52-the-10g-direct-link--plugged-in-on-demand-not-left-connected)), so an 8 GiB guest takes 2–3 minutes rather than ~20 seconds. Do **not** repoint Migration Settings at `10.10.10.0/24` — that makes every ordinary migration depend on a cable that is out. Plug the cable in and override that one run instead: `qm migrate … --migration_network 10.10.10.0/24 --migration_type insecure` ([5.4](setup/05-network.md#54-using-the-10g-link-for-a-migration)). Slower than *that*, or slower than it was: `grep -E '^(migration|replication):' /etc/pve/datacenter.cfg` — these are two independent keys and they can disagree (Stage 7) — and check `bwlimit` isn't throttling you.
- **The 10G direct link is down — no carrier on pve1's `nic1`, `enp62s0` missing from `ip link` on pve2, or a ring `disconnected` in `corosync-cfgtool -s`** → on this build that is the **normal** state, not an incident: the cable is plugged in for a migration and unplugged again ([5.2](setup/05-network.md#52-the-10g-direct-link--plugged-in-on-demand-not-left-connected)). Nothing scheduled depends on it — `datacenter.cfg` pins migration *and* replication to `192.168.0.0/24`, and corosync membership has never ridden that cable — so the link being out breaks nothing today. What it costs is the second ring, and that bill only arrives when the switch does: the QDevice sits on the same LAN as the membership ring, so a dead switch leaves each node at 1 vote of 3, non-quorate, and with fencing armed **both** nodes self-fence (the table in 5.2). The ring carrying membership is **Link 0**, the `192.168.0.x` LAN; the on-demand cable is **Link 1**, `10.10.10.x` — what [Stage 7](cluster/07-cluster.md) builds and what `/etc/pve/corosync.conf` holds. Match on the `addr =` line rather than the LINK ID all the same: `pvecm` gives Link 0 to whichever address you created and joined on, so the numbering is a fact about this cluster and not about the cabling. The repo's `cluster-health` knows the difference — `ON_DEMAND_LINKS` lists link 1 as allowed to be down, and link 0 deliberately is not in it — but the copies installed on both nodes are still the 2026-09-04 ones, which grep the whole of `corosync-cfgtool -s` for `faulty|disconnected` and draw no distinction at all. Do not read their morning line in either direction: the installed cron file sets no `PATH`, so `corosync-cfgtool` (`/usr/sbin`) is never found, the grep matches nothing, and the check prints `[ OK ] corosync: all links healthy` — which is exactly what it printed every morning from 2026-09-04 to 09-10 with ring 1 genuinely down ([Stage 7](cluster/07-cluster.md)). Run that same copy by hand, where `/usr/sbin` is on PATH, and it warns about this cable instead. Neither answer is worth anything until [2.4](setup/02-post-install.md#24-install-the-helper-scripts-both-nodes) is re-run on that node. To *use* the cable, [5.4](setup/05-network.md#54-using-the-10g-link-for-a-migration); the runbook below is for the day you needed it and it isn't there.
- **The QDevice answers `ping` but refuses SSH** → `openssh-server` isn't installed — the *SSH server* checkbox at Debian's Software selection was missed, and nothing says so until you try. At the console: `ss -lntp | grep ':22'` (empty ⇒ confirmed), then `apt install -y openssh-server && systemctl enable --now ssh` (Stage 8.2). Don't diagnose this with `systemctl status ssh`: trixie socket-activates sshd, so a healthy box reports `inactive (dead)` for the service while `ssh.socket` holds the port.
- **`ssh root@` the QDevice says `Permission denied (publickey)`** → working as designed, and *not* the same fault as the line above: sshd is fine, Debian just ships `PermitRootLogin prohibit-password`. Go in as the normal user and install root's keys (Stage 8.4) — never by flipping `PermitRootLogin yes`.
- **`pvecm qdevice setup` dies with `corosync-qdevice-net-certutil: command not found`** → the `corosync-qdevice` package is missing on the *nodes* (it's the one that ships that tool; `corosync-qnetd` on the QDevice is the other half). The message names no package and arrives only after a page of `INFO` lines that look like success. `apt install -y corosync-qdevice` on **both** nodes, then retry with `--force` — the qnetd database survives the failed run and a plain re-run stops at `nssdb already exists` (Stage 8.5).
- **"cluster not ready - no quorum"** → QDevice down/unreachable; emergency on the surviving node: `pvecm expected 1` (temporary!).
- **VM won't live-migrate** → ISO mounted in the CD drive (remove it) or non-migratable local resources attached.
- **VM crashed after migration** → someone set CPU type `host`; revert to `x86-64-v3`.
- **Migration fails after one node was updated and the other wasn't** → version skew. `pveversion -v` on both, `apt dist-upgrade` the lagging node, then migrate (Stage 16.2 / 20.5).
- **A plain `ssh` from pve2 to pve1 will not go through — `ssh root@pve1` dies at `Could not resolve hostname pve1` (neither node has an `/etc/hosts` entry for the other), and `ssh root@192.168.0.11` stops at *The authenticity of host … can't be established* because `StrictHostKeyChecking` is at its default `ask`, or, from a script or cron with no TTY, at a flat `Host key verification failed` — yet migration and replication between those same two nodes work fine** → both are true at once, and the second is why this sits broken for weeks. PVE never reads root's `~/.ssh`: it builds every internal connection with `-o HostKeyAlias=<node> -o UserKnownHostsFile=/etc/pve/nodes/<node>/ssh_known_hosts -o GlobalKnownHostsFile=none`, and pmxcfs hands both nodes both of those files — so the cluster's own traffic cannot notice a node whose root account can verify no host key at all. Everything *you* type does, and so did [`node-return`](scripts/README.md) until 2026-09-10: its peer probe was a plain `ssh -o BatchMode=yes root@<peer>`, so on the affected node it exited before Gate 1 blaming the network — on the one day you run it, after an outage, on the node that just came back ([16.2](operations/16-maintenance.md#162-returning-a-node-after-a-long-outage-days-to-weeks)). The repo copy now probes with `-o HostKeyAlias=<node>` against `/etc/pve/nodes/<node>/ssh_known_hosts`, the way PVE does, and works from either direction; the copy in `/usr/local/sbin` is still the old one until [2.4](setup/02-post-install.md#24-install-the-helper-scripts-both-nodes) is re-run on that node, so `head -40 /usr/local/sbin/node-return` before you lean on it during an outage. The repo's `cluster-health` also reports this fault in its own right now — `[WARN] ssh: plain 'ssh root@<peer>' fails from this node` — and it is the only automated line that ever will; the installed copy says nothing, which is how the gap between *the cluster can reach the peer* and *you can* sat open for weeks. Repair it from the copy the cluster itself vouches for — never from a fingerprint prompt, and never with `StrictHostKeyChecking=no`, which accepts whatever currently answers the address and is precisely what host keys exist to catch. On the affected node, append pve1's line from `/etc/pve/nodes/pve1/ssh_known_hosts` to `/root/.ssh/known_hosts`, rewriting the first field to `192.168.0.11` — the cluster file is keyed by node name only, and the address is the form you can actually type here. Key it `pve1,192.168.0.11` only if you also add the matching `/etc/hosts` line: a host-key entry for a name nothing resolves buys you nothing, and `ssh pve1` keeps failing one step earlier than the key. Then check the other direction: pve1 answers today only because root there accumulated its own `known_hosts`, one lost file away from the same fault. Do **not** repair it by recreating pve1's `/etc/ssh/ssh_known_hosts -> /etc/pve/priv/known_hosts` symlink on the other node — that shared file is the pre-8.2 arrangement, it still holds only stale `pve1` and `192.168.0.11` lines and no `pve2`, plain `pvecm updatecerts` no longer writes to it (it regenerates `/etc/pve/nodes/<node>/ssh_known_hosts`), and `pvecm updatecerts --unmerge-known-hosts` exists to retire the symlink, which is the direction to move pve1 in when you next touch this.
- **Replication says `no common base to restore the job state`** → the incremental chain is broken (long outage, pruned snapshots, or a `qm rollback`). Delete the job, remove the stale volumes on the target, recreate it — you get a full transfer.
- **A stopped VM keeps restarting itself** → it's an HA resource; `ha-manager set vm:<id> --state stopped` instead of `qm stop`.
- **A node was shut down and rebooted, and its VMs didn't come back** → two causes, in this order. (1) `onboot` is 0 — Proxmox's default for every new VM; only HA guests (1021/1022) start on their own, so 1023 needs the flag: `qm set <id> --onboot 1 --startup order=N` (Stage 10, "Start at boot"). (2) The node booted **inquorate** — other node *and* QDevice down — so `/etc/pve` is read-only and nothing starts at all, HA included; `pvecm status` first, then 18.5. And after a clean shutdown with `shutdown_policy=migrate`, HA VMs are running on the *other* node by design — they don't fail back (16.2).
- **`pg_upgradecluster` aborts on an extension** → the matching `postgresql-<newver>-postgis-3` package isn't installed. PostGIS is on `template1`, so *every* database needs it (Stage 20.3 step 1).
- **`pg_upgradecluster` says the target cluster already exists** → installing the package auto-created an empty one; `pg_dropcluster <newver> main --stop` first.
- **Postgres is up after a major upgrade but everything is slow** → statistics weren't carried over; `vacuumdb --all --analyze-in-stages`.
- **A playbook run reverts something you fixed by hand on a VM** → working as designed. `native/infra/ansible` owns everything inside the guests; change the role or the variable, not the file on the box.
- **Postgres minors aren't arriving automatically** → `postgres_auto_minor_upgrades` off, or unattended-upgrades broken. `sudo unattended-upgrade --dry-run -d | grep -i postgres` on 1022 and check `/var/log/unattended-upgrades/` (Stage 20.2).
- **A VM answers on a DHCP address, not the one in its Cloud-Init tab** → that tab shows what the hypervisor offers, never what the guest took. Almost always: the VM booted once *before* the IP was set, and cloud-init applies network config per *instance*, not per boot — a plain reboot won't fix it. `qm agent <id> network-get-interfaces` for the truth, then Stage 10 ("First boot"): destroy + `create-vms` if it's still empty, otherwise `cloud-init clean --logs` inside the guest.
- **A VM took its static IP but is unreachable** → your LAN isn't `192.168.0.0/24` (the guide hard-codes it — vmbr0, the gateway, the `create-vms` table), or `.20–.23` sit inside the router's DHCP pool and something else claimed the address (Stage 10, "First boot").
- **SSH asks for no password and refuses the cipassword** → working as designed: Canonical's cloud image ships `PasswordAuthentication no` in `/etc/ssh/sshd_config.d/60-cloudimg-settings.conf`, from the first boot. The cipassword is the *console* login. Get in with a key, from pve1 (Stage 10, "SSH access").
- **`ssh-copy-id` can't seed a key on a new VM** → it needs password auth to install the key, and there is none (above). Deliver it from something already trusted instead — from pve1: `ssh devops@<ip> 'cat >> ~/.ssh/authorized_keys' < key.pub` — or add it to `vm_keys.pub` and re-apply `--sshkeys` (next bullet). After Stage 11, the right place is `ansible_ssh_extra_public_keys` (21.6).
- **`Permission denied (publickey)` from my workstation, but pve1 gets in fine** → only the keys in the template's `--sshkeys` file exist on a fresh clone. Add yours to `/root/.ssh/vm_keys.pub`, `qm set <id> --sshkeys` + reboot (Stage 10, "From your workstation"). `ssh -J` does not help — it still authenticates *you* to the VM.
- **`ssh devops@<vm>` from pve1 stopped working after a playbook run** → `ssh_authorized_keys_exclusive: true` with the node root keys missing from `ansible_ssh_extra_public_keys` — the run deleted them from every VM. Add both nodes' `id_ed25519.pub` to the list and re-run; until then get in from your workstation or the console (Stage 21.6).
- **Locked out of a VM over SSH** → Proxmox console + the `--cipassword` (Stage 21.4). No cipassword set → mount the VM disk from the hypervisor and edit `authorized_keys` by hand.
- **SSH accepts a password and it shouldn't** → `/etc/ssh/sshd_config.d/99-key-only.conf` missing (cloud-init flipped `ssh_pwauth` on) — re-run the playbook; the `common` role pins key-only (Stage 21.4).
- **pve1 died hard when the UPS ran dry** → expected on this build: the UPS has no data path to pve1, so NUT is disabled and nothing can signal the shutdown ([4.6](setup/04-ups.md#46-disabled-on-this-build)). Confirm Postgres finished crash recovery, then decide whether a cable is worth it. If you *have* since wired the UPS up, then it's NUT not running or not answering — `upsc ups@localhost` should say `OL` (Stage 4).
- **A VM with an unexpected 19xx ID exists** → a restore drill that failed (kept for inspection) or ran with `--keep`; look, then `qm stop <id> && qm destroy <id>` ([`restore-drill`](scripts/README.md)).
- **No morning mail, ever, even when something's wrong** → assume the mail is generated and then discarded at the far end, because every local proof passes while that happens. On both nodes there is no `/etc/pve/notifications.cfg` at all, so every notification — the cron scripts' `system-mail` and PVE's own `vzdump`, `replication` and `fencing` alike — takes the built-in `mail-to-root` **sendmail** endpoint into local postfix, which delivers straight to the recipient's provider from the house's WAN address and is answered `550 5.7.1 Service unavailable, Client host […] blocked using Spamhaus`; postfix logs `status=bounced`, then `removed`. Nothing is retained — `/var/mail/root`, `/var/spool/mail` and the queue are all empty — so there is no backlog to find later, and the envelope sender is `root@<node>.local`, which nothing can align to SPF or DKIM even from a clean IP. A `sendmail` endpoint's **Test** button never reaches the far end, and `echo test | mail -s test root` proves that same local half; the only place the truth is written down is `journalctl -t postfix/smtp --since=-1d | grep -E '550|status=bounced'`, run on both nodes. [15.3](ha/15-ha.md#153-notifications) predicted exactly this and its step 1 is the repair: a real submission service, authorised for a From address on a domain you control. Until that is done the whole native alert layer is dead and the infra-report POST to the app (`platform/docs/adr/0015-infrastructure-verification.md`) is the only channel still reporting — its freshness check is all that stands between you and a silent month. Debug the transport first and the matcher second: a matcher narrowed to `vzdump`+`replication` silences every script in `scripts/` without looking broken, but it cannot be your fault while nothing leaves the node at all.
- **The morning mail and an interactive run disagree — `[FAIL]` on NVMe drives that `smartctl -H` calls `PASSED`, or a check that reports `'<tool>' is not on PATH`** → cron runs with `PATH=/usr/bin:/bin`, which excludes `/usr/sbin`, where `smartctl`, `corosync-cfgtool`, `ha-manager`, `qm`, `dmidecode` and `lsmod` live. `/etc/cron.d/pve-helper-scripts` now sets `PATH=/usr/sbin:/usr/bin:/sbin:/bin` and the checks refuse to judge hardware they never spoke to — but a node still running what it installed before 2026-09-10 has neither, and there a missing tool is silent in *both* directions: every healthy NVMe reads `[FAIL]` (no `PASSED` in the empty output) while a corosync ring that has been down for days reads `[ OK ]` (no `disconnected` in a `command not found`). The false alarm is what you notice; the false all-clear is what costs you. Compare the two environments directly — `env -i PATH=/usr/bin:/bin /usr/local/sbin/cluster-health` against a plain `cluster-health`. Fix by `git pull` and re-running [`install-scripts.sh`](scripts/README.md) on **both** nodes ([2.4](setup/02-post-install.md#24-install-the-helper-scripts-both-nodes)): it rewrites the cron file *and* the scripts. Adding the `PATH` line by hand silences tonight's mail but leaves the checks unguarded, so the next tool that isn't installed lies the same way.
- **The admin UI shows a node red, or a `[FAIL]` for something that is demonstrably fine on the box** → what the app shows is a clipped summary of a run nobody watched, so re-run the check on the node itself — plain `cluster-health`, no arguments — before you either believe it or dismiss it. Two things distort it. (1) The nightly ingest runs whatever copy sits in `/usr/local/sbin`, which is not this repo's copy until someone re-runs [`install-scripts.sh`](scripts/README.md) ([2.4](setup/02-post-install.md#24-install-the-helper-scripts-both-nodes)). That is what produced the 2026-09-10 false red: a cron file with no `PATH`, so `smartctl` was absent and four healthy NVMe drives reported `[FAIL]` while `corosync-cfgtool` was absent and a ring down for six days reported `[ OK ]` — wrong in both directions, and the vacuous OK was the dangerous half (previous bullet). `head -40 /usr/local/sbin/cluster-health` is what tells you whether the `PATH` line and the per-tool `require` guards are on *that* node. (2) The app clips the evidence: the ingest joins the printed lines and stores a capped string, and only that string is persisted — the raw lines are kept nowhere, so evidence is destroyed at ingest rather than merely hidden. Until 2026-09-10 the cap was 300 characters and the lines were joined in script order, which put the NVMe block, near the end, permanently past the cut; it is now 2000 with `[FAIL]` lines sorted ahead of `[WARN]`, so the reason you can read is usually the real one — but a long run still loses its tail, and the verdict is always computed over every line, so a red is trustworthy even when its stated reason isn't. The untruncated text exists in exactly two places: the node's own output, and root's morning mail — assuming that still arrives (two bullets up). And the UI keeps showing the stored string until the next nightly run, so a fix you make at noon proves nothing until tomorrow morning.
- **A node lost quorum but never rebooted itself** → fencing isn't armed, and every automatic-recovery row in 18.3 is void until it is. `systemctl is-active watchdog-mux` on that node; if it's dead, or `softdog` was blacklisted/unloaded, or a second `watchdog` daemon is holding `/dev/watchdog`, that's the cause (Stage 15.4). Prove the fix with the isolation drill, not by reasoning about it.
- **An HA resource sits in `error` and won't start** → `max_restart` and `max_relocate` are both exhausted, which means it failed to start on *both* nodes — the disk image or the guest is the problem, not HA. Fix the cause, then `ha-manager set vm:<id> --state started` to clear it (Stage 15.1).
- **[`backup-verify`](scripts/README.md) says `no vzdump job is scheduled anywhere in the cluster` — or prints nothing at all** → the same fault seen through two versions of the script, and either way *nothing is being backed up*. Check substance, not exit codes: `ls /etc/pve/jobs.cfg` (absent ⇒ no job exists), `grep -c vzdump /var/log/pve/tasks/index` (`0` ⇒ not one has ever run), `ls /var/lib/vz/dump`. Create the job in [17.3](backup/17-backup-restore.md#173-the-scheduled-job); it needs the USB drive on the node the guests actually run on ([17.2](backup/17-backup-restore.md#172-backup-storage--the-usb-drive)). **The silent variant is the dangerous one, and it means your scripts are stale.** Until 2026-09-10 both helpers asked a per-node question — *is the drive here?* — and answered "no drive here" with `exit 0` and no output at all (`cluster-health`: `[ OK ] backup: no USB storage on this node (it lives on the peer)`). That branch assumes some other node is covering this and never tests it, so with the drive on *neither* node both nodes took it: two silent passes over five unverified tiers *and* the WAL-slot check, two green lines each certifying that the drive is on the other one, and an app that recorded "exit 0, no output" as a pass. Both scripts now ask the cluster-wide question instead — `jobs.cfg` and `vzdump.cron` live in pmxcfs and read identically from either side — so a node still running the old copy is what to fix first: re-run [2.4](setup/02-post-install.md#24-install-the-helper-scripts-both-nodes) on both, and treat any `backup-verify` silence from before that date as unverified rather than as a pass. Until the job exists, the only copy of the database is the in-VM nightly dump on 1022 (`/opt/postgres/backups`), which leaves that VM by no route except the pve1→pve2 replication. What checks it is `backup-verify`'s `pg-dump:` line — age *and* size, over the network from either node, below the USB gate and so indifferent to which node holds the drive — and on the installed copies it has never been reached, for the same `exit 0` reason as everything else here. Re-installing is necessary and not sufficient: pve1's `ssh` to 1022 is still pinned to the host key that VM had before the 2026-09-05..07 rebuild, and the repaired script says so — `[FAIL] pg-dump: … the state of the only surviving database copy is UNKNOWN` — rather than manufacturing a pass out of a connection failure ([21.7](operations/21-credentials.md#217-the-fourth-kind-the-pins-nobody-inventories)). The WAL stream on the QDevice is *not* a second copy: WAL replays onto a physical base backup, a `pg_restore`d logical dump has neither the LSN nor the layout to replay onto, and no base backup exists anywhere ([17.5](backup/17-backup-restore.md#175-a-fourth-tier-for-the-database)).
- **[`backup-verify`](scripts/README.md) says the WAL slot is inactive** → `pg-receivewal` on the QDevice is down — `systemctl status pg-receivewal` there; if it loops, it's `.pgpass`, `pg_hba`, or the network (Stage 13.3/13.5).
- **`pg_receivewal: password authentication failed for user "walreceiver"`, looping every 10s** → `.pgpass` on the QDevice disagrees with `postgres_wal_stream_password`. Fix the *file*, not the database: the role re-runs `ALTER ROLE … PASSWORD` on every playbook run, so Postgres always matches `vault.yml`. Usual cause is punctuation — `.pgpass` splits on `:` (escape as `\:`) and the role interpolates the value into SQL, so `'` breaks it too. Keep that secret alphanumeric (Stage 13.2).
- **`pg_stat_replication` returns 0 rows / `pg_receivewal: no pg_hba.conf entry for replication connection from host`** → 1022 doesn't trust the QDevice's address. `postgres_wal_stream_enabled` is false (the `pg_hba` block never rendered) or `postgres_wal_stream_cidr` still holds an old IP — the `/32` has to equal the QDevice's *current* address. Fix both in `group_vars/all/main.yml` and re-run `--limit postgres`. Correcting the CIDR alone costs no outage: the `pg_hba` template deliberately notifies a *reload* — the handler is `SELECT pg_reload_conf()`, because an access CIDR moves every time a client does. It is turning `postgres_wal_stream_enabled` on that bounces the server, and for a different reason — that branch also writes `max_slot_wal_keep_size` and `listen_addresses`, and those two notify a restart (Stage 13.1/13.3).
- **`pg_wal` growing on 1022** → the WAL receiver has been down a while; the slot retains WAL up to `max_slot_wal_keep_size` — **8GB on this build**, not the role's 10GB default, and the arithmetic for "how long can I leave it" is built on that number, so ask the server rather than a file ([13.1](ha/13-wal-stream.md#131-enable-it-on-the-database-side)) — then breaks the stream instead of the disk. Fix the receiver, then drop + recreate the slot (Stage 13.5).
- **After a Postgres major, the WAL stream won't reconnect** → the QDevice's client is the old major; install the matching `postgresql-client-NN` (Stage 13.5 / 20.3).
- **No app logs in Grafana** → check in order: `alloy` active on 1021 (`systemctl status alloy`), the `[monitoring]` group exists in `hosts.ini` (Alloy auto-discovers 1023 from it — no group, no target), `loki_bind_address`/`grafana_bind_address` actually set to 1023's IP and not left on the loopback default (Stage 11.4/11.7).
- **`docker compose ps` on 1023 says `permission denied ... /var/run/docker.sock`** → `devops` is not in the `docker` group. No role in `native/infra/ansible` puts it there, deliberately — that group is root-equivalent on the VM — so the supported answer is to prefix every `docker` command with `sudo` (Stage 11.6). You will not meet this on the live 1023: `getent group docker` there reads `docker:x:109:devops` and `docker ps` runs unprivileged (verified 2026-09-10). That is hand-applied drift, not the design — no playbook reverts it and no rebuild reproduces it, so the symptom comes back the day the VM is recreated.
- **Grafana loads from the VM but not from my workstation** → `monitoring_allowed_cidr` unset or doesn't cover your subnet; the UFW rule on 1023 is what opens it beyond the VM itself (Stage 11.4).
- **Postgres (1022) logs don't show up in Grafana** → expected today, not a bug: Alloy only runs on the app host (Play 2); 1022's logs stay in the journal — `journalctl -u postgresql@18-main` (Stage 11.7).
- **`psql`/pgAdmin from my workstation to 1022 times out** → working as designed: `postgres_app_cidr` is the app VM's `/32`, so only 1021 gets through UFW/`pg_hba.conf`. Opt in with `postgres_extra_cidrs` and re-run the playbook (Stage 11.8).
- **Proxmox shows a VM at ~80% memory but nothing on it is working hard** → the summary panel counts page cache as used, and Linux fills free RAM with cache deliberately, reclaiming it the moment anything asks. The guest has the truth: `free -h` — read the **`available`** column, not `free` — plus `/proc/pressure/memory`. A non-zero PSI `full` average is real pressure; a large `buff/cache` is not. These guests run without swap, so `si`/`so` in `vmstat` stay at zero whatever happens and prove nothing on their own. A healthy 1021 sits near 800 MiB of its 8 GiB with ~6 GiB cached, which the panel reports as ~80%.
- **`systemctl enable` says "the unit files have no installation config"** → that unit is *static* — it's meant to be started by something else (a udev rule, a timer, a target), not enabled. Use `systemctl start`; `qemu-guest-agent` is the one you'll meet here, on the ISO template route (Stage 9.8d — the primary route injects it without ever running systemctl). Beware `enable --now` on a static unit: the enable fails first, so it never starts either.

## Runbook — the 10G link is down

Cable pulled, NIC dead, Thunderbolt adapter dropped off — or simply unplugged after the last migration, which on this build is where it normally lives ([5.2](setup/05-network.md#52-the-10g-direct-link--plugged-in-on-demand-not-left-connected)). **corosync takes care of itself** — the LAN ring (`192.168.0.x`) carries membership and always has, so the cluster stays quorate and `/etc/pve`, HA and quorum are untouched. What you lose is ring redundancy, not the cluster.

**Match links by address, not by number.** `grep ring /etc/pve/corosync.conf` before you use any link number: here `ring0_addr` is the `192.168.0.x` LAN and `ring1_addr` the `10.10.10.x` cable, as [Stage 7](cluster/07-cluster.md) builds them. The numbering is per-cluster and invisible from the network — `pvecm` gives Link 0 to whatever address you create and join on — so a `corosync-cfgtool -s` block read by LINK ID alone is a guess, and the guess that costs you the outage is the one that sends you hunting a LAN fault that isn't there.

The two ends also fail differently, which is worth knowing before you diagnose anything. pve1's X550 port (`nic1`) is always present and simply loses carrier: `ip -br link` shows it DOWN, `ethtool nic1` says `Link detected: no`. pve2's Thunderbolt dock (`atlantic`, `enp62s0`) **disappears from `ip link` altogether** while `/etc/network/interfaces` still configures it — the config reads healthy and the interface is not there. `boltctl list` and `journalctl -k | grep -i thunderbolt` tell the cases apart, and that dock has enumerated and vanished again inside a minute, so an interface that is present now proves nothing about ten minutes ago.

Migration and replication are already on the LAN and stay there: `datacenter.cfg` reads `migration: secure,network=192.168.0.0/24` and `replication: network=192.168.0.0/24,type=secure`, which is step 1 below, applied permanently and deliberately — nothing scheduled is allowed to depend on a cable that is normally out. Step 2 is *not* in force: this cluster has no `bwlimit` at all (`pvesh get /cluster/options` returns none), and that is the one below still worth doing. Everything here needs quorum, which you have — the LAN ring plus the QDevice.

**1. Confirm migration and replication are on the LAN** — a check, not a change: this is already applied and permanent here, and repointing it mid-incident costs you the minutes you needed ([18.3](ha/18-failover.md#183-scenario-table)). `cat /etc/pve/datacenter.cfg` first. If a cluster genuinely is pointed at the 10G subnet: Datacenter → Options → Migration Settings → Network `192.168.0.0/24`, or from a shell on either node:

```bash
pvesh set /cluster/options --migration type=secure,network=192.168.0.0/24
```

Applies immediately, no service restart, and only *new* migrations and replication runs pick it up. Keep `type=secure`: at 1G, SSH isn't the bottleneck, and this traffic now crosses a shared LAN instead of a private cable. (The property string replaces the whole line, which is why `type=` is repeated.) Clearing the Network field works too — the default is the address the node's own hostname resolves to, which is `192.168.0.x` anyway — but being explicit keeps the next person from wondering.

**2. Set the bandwidth limit. This is the part that bites, and it is the step still outstanding.** [Stage 7](cluster/07-cluster.md) prescribes `migration=60000` for exactly this reason, and this cluster has no `bwlimit` key at all, so migration and replication may take the whole wire. 1G tops out around 118 MB/s, and while the cable is out the LAN is the *only* corosync ring as well as every VM's path (and the offsite sync's, on the day one exists — nothing ships off these nodes today, [Stage 17](backup/17-backup-restore.md)) — saturating it means token jitter on the one remaining ring, and in the bad case a node fencing itself in the middle of a large replication.

```bash
pvesh set /cluster/options --bwlimit migration=60000    # KiB/s ≈ 60 MB/s
```

Leave roughly half the link free. Check the per-job rate limits in each VM's Replication panel too, and keep in mind the same string-replacement caveat if you already have `restore=`/`clone=` values set.

**3. Verify.**

```bash
cat /etc/pve/datacenter.cfg      # migration: secure,network=192.168.0.0/24
corosync-cfgtool -s              # the 10.10.10.x ring disconnected, the 192.168.0.x one connected — read the addr, not the LINK ID
pvesr status                     # jobs return to OK on their next cycle
ha-manager status
```

Then run the [Stage 14](ha/14-live-migration.md) ping test. It works, about 10× slower: an 8 GiB guest moves in 2–3 minutes rather than ~20 seconds, and a write-heavy 1022 needs more dirty-page iterations to converge.

**Do not remove the dead ring from `corosync.conf`** — here that is `ring1_addr`, the `10.10.10.x` one — the two lines differ by one character and only one of them is the ring holding the cluster up. It stays configured, corosync reports the link `disconnected` (`corosync-cfgtool -n` still shows it `enabled`), and it comes back on its own when the hardware does — a re-seated Thunderbolt adapter re-enumerating is enough. Delete the wrong `ringN_addr` line and you have removed the ring currently holding quorum; and editing corosync while the other ring is the only one carrying the cluster is how you lose that one too, with `/etc/pve` read-only and no second path to fix it from. Removing this link permanently is a decision that was taken and rejected — [5.2](setup/05-network.md#52-the-10g-direct-link--plugged-in-on-demand-not-left-connected) has the reasoning.

**Going back**, once the cable is in or the NIC is replaced: on pve2 `ifup enp62s0` (the interface did not exist a moment ago) → `ping 10.10.10.x` → `corosync-cfgtool -s` with both rings connected. That is the whole of it — `datacenter.cfg` stays pinned to the LAN, and the 10G path is asked for per migration instead ([5.4](setup/05-network.md#54-using-the-10g-link-for-a-migration)). Never point migration at a link you have not proved first: that is exactly the [16.2](operations/16-maintenance.md#162-returning-a-node-after-a-long-outage-days-to-weeks) mistake in miniature, and it is half the reason the pin is permanent.

If the 10G hardware isn't coming back soon, a cheap USB 2.5G NIC at each end restores the direct link — and with it the second ring — without touching the design. corosync wants latency, not throughput.

### Optional — collapsing everything onto one network

If the 10G link isn't worth repairing and you'd rather run the whole cluster on `192.168.0.0/24`, this is the full sequence. Read the trade-off at the end before starting; it is not a small one. Do it with both nodes up and physical console access available.

**1. Migration and replication** — steps 1 and 2 above, kept permanently, lower bandwidth limit included.

**2. Back up the cluster config**, on both nodes:

```bash
cp /etc/pve/corosync.conf /root/corosync.conf.bak
cp /etc/corosync/corosync.conf /root/corosync.local.bak
```

[`pve-config-backup`](scripts/README.md) already covers these, but take the copy anyway — you're about to edit the one file that can lock you out of your own cluster.

**3. Rewrite corosync to a single link.** On **one** node only; `/etc/pve` propagates it. Proxmox's procedure is edit-a-copy-then-move, so a half-written file is never live:

```bash
cp /etc/pve/corosync.conf /etc/pve/corosync.conf.new
nano /etc/pve/corosync.conf.new
```

In each `node { }` block: set `ring0_addr` to that node's `192.168.0.x` and delete its `ring1_addr` line. In `totem { }`: delete the `interface { linknumber: 1 }` block. Then **increment `config_version`** — corosync ignores the file otherwise, and the symptom is nothing happening at all. Finally:

```bash
mv /etc/pve/corosync.conf.new /etc/pve/corosync.conf
```

corosync reloads on its own. Watch `journalctl -u corosync -f` on both nodes, then `pvecm status` (Quorate: Yes) and `corosync-cfgtool -s` — a single LINK 0, on `192.168.0.x`.

If it goes inquorate instead, on each node: `systemctl stop pve-cluster corosync`, then `pmxcfs -l` — local mode makes `/etc/pve` writable again — restore both backups, `systemctl start corosync pve-cluster`.

**4. Re-seat the QDevice.** Its membership is bound to the ring addresses you just changed, so remove and re-add rather than hoping:

```bash
pvecm qdevice remove
pvecm qdevice setup 192.168.0.10 -f
pvecm status        # Total votes: 3
```

**5. Clean up the 10G interface** — delete its stanza from `/etc/network/interfaces` on each node, `ifreload -a`, and confirm `ip route | grep default` is still exactly one line ([5.3](setup/05-network.md#53-verify)).

**6. Update the guide to match the cabling**: [5.2](setup/05-network.md#52-the-10g-direct-link--plugged-in-on-demand-not-left-connected), Stage 7's two links and migration network, and the two 10G rows in [18.3](ha/18-failover.md#183-scenario-table). A network description that no longer matches reality is worse than none, and this one gets read on the day something is on fire.

**What you give up.** With the cable in, a dead switch or router is survivable: the nodes still see each other over the direct link, hold 2 of 3 votes, stay quorate, and the VMs keep running — you lose client access, nothing more ([18.3](ha/18-failover.md#183-scenario-table)). With it out, which is its normal state here ([5.2](setup/05-network.md#52-the-10g-direct-link--plugged-in-on-demand-not-left-connected)), you are already living the other half of that trade: the same failure isolates both nodes *and* the QDevice, each node holds 1 vote of 3, both go inquorate, and with fencing armed both self-fence — one switch failure becomes a full cluster reset, and the VMs come back when the switch does. What collapsing takes away is the *recovery*. Today that second ring is one cable away from existing again; afterwards it is a corosync edit away, on a cluster that is inquorate and `/etc/pve` read-only at exactly the moment you want it. Step 5 takes a second thing with it, quietly: with the `10.10.10.x` stanza gone from `/etc/network/interfaces` there is no subnet left to override a migration onto, so the per-migration fast path goes too ([5.4](setup/05-network.md#54-using-the-10g-link-for-a-migration)) and every future migration is a 1G migration — that is the whole reason the cable exists, given up in a step that reads like tidying.

That is the price of the simpler diagram, and it is why the link stays declared even though it is usually unplugged: a ring you can restore with a cable is worth more than the tidiness of a file with one fewer line in it.
