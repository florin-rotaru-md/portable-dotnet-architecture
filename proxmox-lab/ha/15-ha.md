# Stage 15 — HA (automatic failover)

*Part of the [Proxmox lab guide](../README.md).*

## 15.1 Which VMs get HA

**Datacenter → HA → Resources → Add** for **1021 (app)** and **1022 (postgres)** only.

Leave 1020 (control) out — it serves no users, and fewer moving parts during an incident is a feature. You start it manually when you need Ansible.

Leave **1023 (monitoring) out too**, for the same reason. It's an observability tool, not something users depend on: if its node dies, dashboards and the last half-hour of logs are unavailable until you migrate or restart it by hand from the latest replica ([Stage 12](12-replication.md)) — an acceptable gap, and one less VM the HA manager has to reason about while it's busy recovering the two that actually matter.

> **Out of HA is not the same as never coming back.** HA answers "a node *died*"; the plain `onboot` flag from [Stage 10](../vms/10-vms.md#start-at-boot--what-comes-back-after-a-node-reboot) answers "a node was *rebooted*", and 1023 has it — a maintenance reboot brings monitoring back on its own, a node death doesn't. For the two VMs here, HA replaces that flag entirely: boot-time `startall` skips HA-managed guests and the HA stack starts them itself, as soon as the node is quorate.

### What goes in the dialog

Every field can stay on its default, but two of them decide what happens when a recovery *doesn't* work, so they are worth understanding once:

| Field | Value | What it means |
|---|---|---|
| **Resource** | `1021`, then `1022` | one entry per VM — there is no multi-select |
| **Request State** | `started` (default) | the state the CRM works toward. `stopped` is what [20.3](../operations/20-upgrades.md) uses to keep HA's hands off during a Postgres major; `disabled` is `stopped` without relocation; `ignored` drops the resource out of the manager entirely, back to plain `qm` control |
| **Max. Restart** | `1` (default) | how many times the LRM retries the start **on the same node** before giving up on it |
| **Max. Relocate** | `1` (default) | how many times it then tries **another node** before parking the resource in `error` |
| **Comment** | optional | |

There is no *Group* field to fill in — node placement moved to the **Rules** panel, which this build leaves empty ([15.5](#155-rules--and-the-failback-flag-that-is-on-by-default)).

Leave the two counters at 1. They look like a place to buy resilience and they aren't: if Postgres fails to start on pve1 *and* fails to start on pve2, the disk image is the problem, and a fourth automated attempt only delays the moment you find out. `error` is the state you want — it stops the loop and shows up in `ha-manager status` and in the daily [`cluster-health`](../scripts/README.md). Clear it with `ha-manager set vm:1022 --state started` once the cause is fixed.

Same thing from the shell — this is the form [17.7](../backup/17-backup-restore.md#177-restore--pick-your-scenario) and [19.2](../operations/19-node-replacement.md#192-approach-a--clean-swap-step-by-step) use when a restored or rebuilt VM goes back under HA:

```bash
ha-manager add vm:1021 --state started
ha-manager add vm:1022 --state started
ha-manager status              # both listed as (<node>, started)
```

## 15.2 Shutdown policy — important

**Datacenter → Options → HA Settings → `shutdown_policy` = `migrate`**

Default behavior on a clean node shutdown is to *stop* HA VMs and restart them on the other node. With `migrate`, a clean shutdown triggers a **live migration** instead — zero downtime.

This ties directly into the laptop battery script (Stage 3.2): on a long outage where the UPS is exhausted and the ZBook's battery hits 10%, the script issues a clean shutdown → the VMs live-migrate to pve1 on their own before pve2 powers off. Unattended, graceful failover.

## 15.3 Notifications

Everything that guards this build reports by mail and stays quiet when healthy — replication, backups, the fencing events from [15.4](#154-the-watchdog--what-fencing-actually-rests-on), package updates, and the nightly [helper scripts](../scripts/README.md) with their `MAILTO=root`. A silently failing replication job means your RPO quietly drifts from 1 minute to hours. You want to find out that day, not during a failover.

Two things have to be true, and only the first is obvious.

**1. A target that can actually send.** **Datacenter → Notifications → Add → SMTP**:

| Field | Value |
|---|---|
| Server / Port | your provider's submission host — 587 with STARTTLS, or 465 with TLS |
| Encryption | `STARTTLS` or `TLS`, never `insecure` |
| Username / Password | the provider's credentials, into the password manager ([0.5](../setup/00-preparation.md#05-keys--generate-all-of-them-now)) |
| From Address | an address on a domain you control, which that provider is authorised to send for |
| Recipient | where you actually read mail |

Use a real submission service — the transactional sender the app already uses is the obvious candidate. What does not work is letting the node deliver straight to your mailbox: that's a residential IP with no SPF or DKIM alignment behind it, so the mail is dropped silently at the far end, which is the precise failure this section exists to prevent.

**2. A matcher that routes the events you care about to it.** PVE classifies every notification by `type`, and the default matcher forwards all of them. If you narrow it, these are the ones this build leans on:

| `type` | Raised when | Why it matters here |
|---|---|---|
| `replication` | a replication job fails | your RPO is drifting *right now* ([Stage 12](12-replication.md)) |
| `vzdump` | a backup job fails | [17.3](../backup/17-backup-restore.md#173-the-scheduled-job) — the classic three-weeks-without-backups discovery |
| `fencing` | a node was fenced | the HA stack acted; something died ([18.2](18-failover.md#182-anatomy-of-an-unplanned-failover)) |
| `system-mail` | anything writes to local root's mailbox | this is what carries `cluster-health`, `backup-verify` and smartd — the whole cron reporting channel |
| `package-updates` | updates are available | low signal, daily; keep or drop to taste |

`fencing` and `system-mail` are the two people leave out. The first is the only automatic notice you get that HA did something; the second is not a Proxmox job at all — it's every script in [scripts/](../scripts/README.md).

**Then prove both paths, because they are different paths.** The target's **Test** button proves SMTP and nothing more. The second proof is that mail addressed to local root turns into a `system-mail` notification and leaves through the same target — run it on **both nodes**:

```bash
echo "mail path test $(hostname) $(date -Is)" | mail -s "pve mail test" root
```

That is the same check [23.3](../operations/23-drill-book.md#233-the-calendar) puts on the quarterly calendar, for the reason that makes this section load-bearing: a healthy quarter and a dead mail path look exactly alike from here.

## 15.4 The watchdog — what fencing actually rests on

[18.2](18-failover.md#182-anatomy-of-an-unplanned-failover) says a node that loses quorum resets itself within ~60 seconds, and that this self-fencing is what makes automatic recovery safe rather than reckless. The mechanism behind that sentence is a watchdog device: `watchdog-mux` holds `/dev/watchdog` open for its whole lifetime and multiplexes it — the HA services (LRM and CRM) connect to it as clients and keep their end alive, and when a node stops being allowed to run HA, the mux stops updating the device. The countdown expires and the box resets itself.

**Which watchdog this build uses: `softdog`.** Proxmox arms a hardware watchdog only when one is named in `/etc/default/pve-ha-manager`; with nothing set, it falls back to the Linux kernel's software watchdog. Nothing in this guide sets it, and neither node has IPMI, so `softdog` is the realistic answer on both.

That is an accepted trade, not an oversight — but it is worth knowing exactly what it does and doesn't cover:

- **It covers the failure this build actually fears:** a node that is alive but no longer quorate — pulled cable, dead switch port, corosync wedged, a link that flaps. The kernel is running, so the countdown runs, and the node reboots itself before the survivor starts the same VMs. That is the split-brain case.
- **It does not cover a hard kernel hang**, where the module that must count down is frozen along with everything else. A hardware watchdog is separate silicon and survives that; `softdog` doesn't. The consolation in *this* topology is that a hung node isn't writing to anything shared either — storage is local ZFS, replicated, never mounted twice — so the cost is a recovery that waits out the HA manager's own timeouts, not a corrupted database.

**Verify it on both nodes.** Nothing else in the guide, and nothing in the UI, will tell you the watchdog never got armed:

```bash
systemctl is-active watchdog-mux         # active
journalctl -u watchdog-mux | tail -3     # names the driver it opened
lsmod | grep -E 'softdog|iTCO_wdt|wdat_wdt'
```

[`cluster-health`](../scripts/README.md) checks the first of those daily, from Stage 2.4 onward.

Switching to a hardware watchdog, if a drill ever gives you a reason to, is one line and a restart:

```bash
echo 'WATCHDOG_MODULE=iTCO_wdt' >> /etc/default/pve-ha-manager
systemctl restart watchdog-mux
```

⚠️ **Two quiet ways to break fencing.** Don't blacklist or unload `softdog` while tidying up modules — you remove the countdown and everything else still looks healthy. And don't install the standalone `watchdog` daemon alongside it: two processes competing for `/dev/watchdog` end with one of them not getting it. Whichever you run, the proof is [18.6 #4](18-failover.md#186-pre-launch-test-plan) — the isolation drill is the only test that exercises this path, which is why a passing plug-pull tells you nothing about it.

## 15.5 Rules — and the failback flag that is on by default

Resources is not the only panel under **Datacenter → HA**. Next to it sits **Rules**, and this build leaves it **empty** — deliberately, and with one flag worth knowing about before you ever change that.

**Why nothing here.** Two nodes, symmetric replication, no primary. There is no preferred node worth encoding; encoding one buys nothing during an incident and costs the behaviour you want after it — a recovered VM should stay where it landed until *you* decide the other node is fit to take it back. [16.2](../operations/16-maintenance.md#162-returning-a-node-after-a-long-outage-days-to-weeks) is that decision, and it has gates a rule cannot check.

**The flag.** Every HA resource carries `failback`, and it defaults to **1**: *return to the highest-priority node available, as soon as that node is back*. Priority comes from **node affinity rules** — so with Rules empty there is no higher-priority node to return to, the flag has nothing to act on, and the cluster behaves exactly as [16.2](../operations/16-maintenance.md#162-returning-a-node-after-a-long-outage-days-to-weeks) describes. An empty panel is the whole reason it behaves that way; nothing else is holding it.

Add one node affinity rule (`ha-manager rules add node-affinity …`) without touching the flag and it wakes up: 1022 starts walking home to a node whose replica may be two weeks stale — automatically, at the worst possible moment. So, **if you ever add a node affinity rule, clear failback in the same sitting:**

```bash
ha-manager set vm:1021 --failback 0
ha-manager set vm:1022 --failback 0
```

**The one rule worth a thought.** The other kind is *resource affinity* — keep resources together, or apart:

```bash
# considered, not adopted in this build
ha-manager rules add resource-affinity app-with-db --affinity positive --resources vm:1021,vm:1022
```

Keeping the app with its database sounds right, and on a larger cluster it would be. Here it is redundant: a failover has exactly one surviving node, so the pair lands together anyway, and the only way they split is you migrating one by hand — a decision, not an accident. It is the first rule to add if a third node ever joins.

## 15.6 Behavior summary

If a node dies suddenly, HA VMs restart on the healthy node within ~2-3 minutes, from the latest replica (data loss ≤ the replication interval). See [Stage 18](18-failover.md) for the full mechanics.
