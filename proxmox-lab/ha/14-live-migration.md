# Stage 14 — First live migration 🎯

*Part of the [Proxmox lab guide](../README.md).*

1. From another computer: `ping -t 192.168.0.21`.
2. Right-click on the VM → **Migrate** → Target: the other node → Migrate.
3. "migration finished successfully" — the ping continues uninterrupted (at most 1 lost packet). Migrate it back as well.

This runs over the 1G LAN, because that is what `/etc/pve/datacenter.cfg` pins migration to and what is guaranteed to be plugged in. For a guest whose RAM or disks make that slow, the 10G cable is connected for the occasion and named explicitly on the command line — the procedure is [5.4](../setup/05-network.md#54-using-the-10g-link-for-a-migration). The UI has no field for it: an override that only applies while a cable is in has no business being a saved default.

If it doesn't finish, [troubleshooting](../troubleshooting.md) lists the causes in the order worth checking — and resist proving the path first with a bare `ssh <peer>`. On this cluster that fails for reasons that have nothing to do with migration: neither node has an `/etc/hosts` entry for the other, so the name form dies at `Could not resolve hostname` before SSH is involved, and by IP the answer is asymmetric: from pve1 it simply connects, while pve2 — which has no `/etc/ssh/ssh_known_hosts` and no entry for pve1 in root's own `known_hosts` — meets first contact instead. At a console that is a prompt, not an error: *The authenticity of host '192.168.0.11 (192.168.0.11)' can't be established … Are you sure you want to continue connecting?*, because `StrictHostKeyChecking` is at its default `ask`. Only a script, or anything else without a TTY, gets `Host key verification failed`. Typing `yes` there pins whatever answered, sight unseen, which is a decision to make deliberately ([21.7](../operations/21-credentials.md#217-the-fourth-kind-the-pins-nobody-inventories)) rather than mid-incident (verified 2026-09-10, both directions). PVE never reads any of those files: it builds every internal call with `-o UserKnownHostsFile=/etc/pve/nodes/<node>/ssh_known_hosts -o GlobalKnownHostsFile=none -o HostKeyAlias=<node>`, and pmxcfs puts both nodes' copies on both nodes — so the path migration and replication use is symmetric and healthy while yours is not. A bare `ssh` failure here is not evidence of anything, and chasing it costs you the outage.
